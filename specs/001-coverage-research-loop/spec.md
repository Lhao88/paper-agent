# Feature Specification: 按覆盖缺口多轮研究

**Feature Branch**: `001-coverage-research-loop`

**Created**: 2026-11-10

**Status**: Draft

**Input**: User description: "只规格化下一次变更：把一次新的研究运行，从「确认提纲后沿固定图走到综述」，改成「用户确认研究规格，再按覆盖缺口多轮调用封闭工具，并把可引用主张写入项目级证据账本」。做完后，新的 coverage 运行必须能看到三件事：检索前确认 3 到 5 个子问题、纳入和排除规则、至少一列抽取字段和每个子问题的覆盖目标；至少两轮检索，第二轮查询来自覆盖缺口；综述里的文献判断能打开到主张，主张落到现有 evidence 行，同一项目的下一次运行能看见已入库论文、钉住项和排除项。legacy 快照、计划版本确认、全文下载范围、旧演示和现有 legacy 测试保持不变。本变更不包含知网或万方全文、开放网页、Agent 互调、角色群聊和更换前端框架。行为细节以 2026-11-08 规划、记忆与工具重构计划第 2、7、9、12 节为准。"

## Clarifications

### Session 2026-11-10

- Q: legacy 与 coverage 如何并存？ → A: 按每条 run 自己的输入快照并存。快照是 legacy 就走原阶段；快照是 coverage 就走规格确认后的多轮循环。同一项目可以同时有两种运行，一条不得改写另一条的快照，后来的进程默认模式也不得改写已写入的快照。
- Q: approve_spec 冻结哪些字段？ → A: 只冻结 coverage 运行。确认成功时写入 `planner_mode`、`max_research_rounds`、`max_actions_per_round`、`max_citation_neighbors`、`max_search_in_paper_calls_per_paper`、`embedding_mode`、`enabled_sources`，以及当时的来源请求上限、模型调用上限和精读篇数上限。确认后只读。legacy 运行不进入 approve_spec。
- Q: 研究循环在哪些条件下停止？ → A: 以下任一成立即停止并进入写作：必填列已满足且本轮没有新的高相关论文；连续两轮饱和；调用、来源或时长预算不足；达到该 run 冻结的 `max_research_rounds`。
- Q: 写作上下文可以读取什么？ → A: 只读已绑定原文跨度的主张和对应原文摘录。不读整篇原文，不读模型调用历史。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 检索前确认研究规格 (Priority: P1)

研究生提交主题和范围后，系统先给出一份可编辑的研究规格，而不是立刻检索。
规格包含 3 到 5 个子问题、纳入和排除规则、至少一列抽取字段，以及每个子问题的覆盖目标。
用户可以修改规则、抽取列和覆盖目标，也可以钉住或排除已知论文。
确认后才开始检索。

**Why this priority**: 没有这份确认，后续轮次无法判断缺口，用户也不能在检索前约束纳入范围。

**Independent Test**: 只完成规格确认时，用户能看见并改完上述内容，且在确认前没有任何论文检索。

**Acceptance Scenarios**:

1. **Given** 用户提交了主题和范围，**When** 系统起草研究规格，**Then** 规格含 3 到 5 个子问题、至少一条纳入或排除规则、至少一列抽取字段，以及每个子问题的覆盖目标。
2. **Given** 草稿里的问题、列或规则编号由起草过程填写，**When** 规格被保存，**Then** 程序重写这些编号，范围以用户请求为准。
3. **Given** 规格尚未确认，**When** 用户增删规则或抽取列、修改覆盖目标、钉住或排除已知论文，**Then** 确认前的页面显示这些修改和覆盖目标，检索仍未开始。
4. **Given** 用户提交的确认版本不是当前计划版本，**When** 用户确认，**Then** 确认被拒绝，检索不开始。
5. **Given** 用户以当前计划版本确认 coverage 运行，**When** `approve_spec` 成功，**Then** 该 run 的输入快照冻结 `planner_mode`、`max_research_rounds`、`max_actions_per_round`、`max_citation_neighbors`、`max_search_in_paper_calls_per_paper`、`embedding_mode`、`enabled_sources`，以及当时的来源请求上限、模型调用上限和精读篇数上限；之后这些值不随进程配置改变。

---

### User Story 2 - 按覆盖缺口进行下一轮检索 (Priority: P1)

确认后的 coverage 运行按轮推进。每一轮先展示覆盖表，再执行有限的封闭动作。
只要必填目标仍有缺口且预算还够，第二轮查询必须来自这个缺口，而不是把第一轮英文词再拼接一次。

**Why this priority**: 这是本次变更相对「确认提纲后沿固定流程走到综述」的核心差别。

**Independent Test**: 用一份已确认、第一轮后仍缺必填列的规格，检查第二轮查询能对应到覆盖表缺口，且与第一轮查询不同。

**Acceptance Scenarios**:

1. **Given** 覆盖运行已确认且账本为空，**When** 第一轮开始，**Then** 所有带必填列的子问题都出现在未满足清单中。
2. **Given** 第一轮结束后某必填列仍未满足且预算足够，**When** 第二轮提出检索，**Then** 第二轮查询来自该覆盖缺口，查询文本与第一轮不同，也不是第一轮英文词的再次拼接。
3. **Given** 规划提出停止，但必填目标未满足且预算仍够检索，**When** 运行时准入处理该停止，**Then** 停止被拒绝，并补一条缺口检索；查询由未满足列的说明和该问题的种子词组成。
4. **Given** 一轮规划出的动作超过 6 个，或包含未知论文、未启用来源、超预算或越权精读，**When** 准入结束，**Then** 这些动作不执行，笔记能看到被拒绝的原因。
5. **Given** 必填列已满足且本轮没有新的高相关论文，或连续两轮饱和，或调用、来源、时长预算不足，或达到该运行冻结的轮次上限，**When** 本轮结束，**Then** 运行进入写作、检查和完成，不再为了填满轮次而空转。

---

### User Story 3 - 从综述打开主张并留给下一轮 (Priority: P2)

coverage 运行的写作上下文只读已绑定原文跨度的主张和对应原文摘录。
读者能从文献判断打开对应主张，主张指向一条已有证据。
同一项目的下一次运行在检索前就能看见已入库论文、钉住项和排除项。

**Why this priority**: 前两则故事产生过程；这一则让结论可追溯，并让项目记忆跨运行保留。

**Independent Test**: 完成一次含主张的 coverage 运行后，从综述打开每一条文献判断，并新建同项目运行，核对库、钉住项和排除项。

**Acceptance Scenarios**:

1. **Given** 抽取得到的原文跨度通过既有核对，**When** 主张写入，**Then** 该主张指向同一篇论文上已有的 evidence 记录，页码来自解析结果。
2. **Given** 综述中有文献判断，**When** 读者打开该判断，**Then** 能看到对应主张、支持或反驳，以及原来的原文位置。
3. **Given** 同一抽取列上有两条极性相反的主张，**When** 读者查看方法比较，**Then** 两条分成两行，不合并成一个排名。
4. **Given** 某个子问题没有主张，**When** 生成综述，**Then** 该子问题写成未覆盖说明，不生成实验比较。
5. **Given** 同一项目已有入库论文、钉住项和排除项，**When** 用户开始下一次运行，**Then** 检索前能看见这三类记录，被排除的论文不进入新的候选集。

---

### User Story 4 - 旧模式运行保持原路径 (Priority: P1)

已经按旧模式写入快照的运行，仍沿原来的固定阶段走到综述。
在新研究循环完成前，开发默认仍创建旧模式运行。
旧演示和现有旧模式测试继续按原路径通过。

**Why this priority**: 新循环未完成时，不得把现有演示和已有运行改到未完成的路径上。

**Independent Test**: 不启用 coverage 时，一次运行仍依次经过原有阶段，且旧模式预算保持原值。

**Acceptance Scenarios**:

1. **Given** 运行快照是旧模式，**When** 运行执行，**Then** 阶段仍是 plan、approve_plan、retrieve、screen、select、read、analyze、decide、write、validate、finalize。
2. **Given** 新研究循环尚未完成，**When** 开发环境创建新运行，**Then** 默认模式仍是 `planner_mode=legacy`。
3. **Given** 快照已经写为旧模式或 coverage，**When** 之后的进程配置改成另一种模式，**Then** 该运行仍使用快照里的模式。
4. **Given** 旧模式运行已经冻结来源请求上限 20 和模型调用上限 150，**When** 本变更启用 coverage，**Then** 这些旧运行的预算不变；只有 coverage 新运行的快照使用来源请求上限 40 和模型调用上限 180。
5. **Given** 同一项目里一条运行的快照是 legacy、另一条是 coverage，**When** 两条都继续执行，**Then** 各自只沿自己的快照前进，互不改写。legacy 运行不进入 `approve_spec`。

---

### Edge Cases

- 论文没有摘要时，不得仅因没有摘要就判为不相关；摘要筛选缺少摘要文本，论文仍可留在候选中。
- 全文只下载已经纳入的论文，或本轮被选中的论文。被引用本身不构成精读资格。
- 精读只能选择相关性不少于 3，或已被钉住的论文，并且不得超过剩余精读名额。相关性为 2 且未钉住的论文不得精读。
- 一跳引文的论文必须已在本项目库中，且不是排除状态。方向必须指明向前或向后。一次新增不超过该运行冻结的邻居上限，默认 15 篇。
- 篇内片段只针对已有解析文档、且指定必填列仍为空的论文。同一篇超过冻结的调用上限时拒绝，默认每篇 3 次。抽取若引用了这次没有返回的片段，整次抽取失败，不写主张。
- 来源请求或模型调用预算不够任何检索和精读时，本轮停止，笔记原因是预算耗尽。单个动作失败只记录该动作的警告，不把整轮记成未执行的成功。
- 某个来源全部失败时，笔记记录失败，覆盖表记下该来源限制；规划可以换来源或停止。
- 连续两轮都没有新纳入的高相关论文，也没有新填上的必填单元格时，视为连续饱和，可以停止并进入写作。
- 同一论文、同一列、同一证据、同一极性的主张重复出现时，不增加覆盖计数。
- 语言范围含中文，但没有已配置的中文全文来源时，覆盖表写入 `zh_fulltext_not_licensed`，不得改为抓取全文。
- 年份和语言以用户请求为准，在执行时过滤。动作里自带的范围不被采纳。
- 规划连续给出无法执行的动作时，预算允许就补缺口检索；预算不够就停止。不得为了填满轮次而空转。
- 语义排序不可用时，篇内检索仍按现有关键词相关度返回片段，笔记标明当时的排序方式。
- 恢复既有运行前，仍须确认旧的执行进程已经退出。本变更不自动提交或推送代码。
- 同一项目同时有 legacy 与 coverage 运行时，每条运行只读自己的快照。改变进程默认模式不得把已有运行改到另一条路径。
- 必填列已经满足，但本轮仍有新的高相关论文时，不得仅因必填列满足就停止。
- 写作不得因为上下文不够而改读整篇原文或模型调用历史。没有主张的子问题只写未覆盖说明。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在 coverage 运行的检索开始前，让用户确认 3 到 5 个子问题、至少一条纳入或排除规则、至少一列抽取字段，以及每个子问题的覆盖目标。
- **FR-002**: 系统必须重写问题、列和规则编号。范围、年份和语言必须以用户请求为准，不得以起草结果改写用户范围。
- **FR-003**: 用户必须能在确认前增删纳入和排除规则、增删抽取列、修改覆盖目标，并钉住或排除已知论文。确认前必须显示覆盖目标。
- **FR-004**: 确认时核对的 `expected_version` 必须仍指计划版本。计划内容变化后版本必须增加。旧版本确认必须被拒绝。
- **FR-005**: coverage 运行在 `approve_spec` 确认成功时，必须冻结 `planner_mode`、`max_research_rounds`、`max_actions_per_round`、`max_citation_neighbors`、`max_search_in_paper_calls_per_paper`、`embedding_mode`、`enabled_sources`，以及当时的来源请求上限、模型调用上限和精读篇数上限。确认后这些字段只读，不得跟随后来的进程配置。legacy 运行不得进入 `approve_spec`。
- **FR-006**: 每一轮必须先由程序根据项目账本生成覆盖表。覆盖数字不得由模型编造。
- **FR-007**: 每一轮规划必须只依据研究规格、最近两页笔记和当前覆盖表，提出最多 6 个有类型的动作。
- **FR-008**: 封闭动作必须只包括已注册检索、向前或向后的一跳引文、篇内片段，以及现有的摘要筛选、全文阅读和抽取。
- **FR-009**: 运行时准入必须丢弃超预算、未知论文、未启用数据源和越权精读的动作，并在笔记中留下拒绝原因。
- **FR-010**: 必填目标未满足且预算仍够时，系统必须拒绝单独的停止，并补一条由未满足列说明和该问题种子词组成的检索。该补检索必须记为来自缺口，而不是来自第一轮英文词的重复拼接。
- **FR-011**: 在缺口仍在且预算足够的 coverage 运行中，系统必须至少执行两轮检索，第二轮查询必须能对应到覆盖表中的缺口。
- **FR-012**: 全文下载必须只针对已纳入或本轮选中的论文。没有摘要不得被当作不相关。
- **FR-013**: 一跳引文必须只扩展一跳，新论文进入项目库后等待筛选。系统不得因为论文被引用就直接精读。一次动作新增论文数不得超过该运行冻结的邻居上限，默认 15。
- **FR-014**: 篇内片段必须只取自该论文已保存的正文片段。抽取引用了本次未返回的片段时，系统不得写入主张。
- **FR-015**: 主张必须在通过既有原文跨度核对后写入项目级证据账本，并且必须指向同一篇论文上已有的 evidence 记录。页码必须来自解析结果，不得由模型生成。
- **FR-016**: 程序必须只检查综述引用的证据是否存在。语义是否支持必须留给人工核验。
- **FR-017**: coverage 运行的写作上下文必须只读已绑定原文跨度的主张和对应原文摘录。不得读取整篇原文，不得读取模型调用历史。没有主张的子问题必须写成未覆盖说明，不得生成该子问题的实验比较。
- **FR-018**: 支持与反驳必须同时保留。同一列上极性相反的主张在方法比较中必须分成两行。
- **FR-019**: 读者必须能从综述中的文献判断打开到主张，并看到支持或反驳以及原来的原文位置。
- **FR-020**: 同一项目的下一次运行必须在检索前看见已入库论文、钉住项和排除项。被排除论文不得进入新的候选集。
- **FR-021**: 系统必须在以下任一条件成立时停止研究循环并进入既有写作、检查和完成：必填列已满足且本轮没有新的高相关论文；连续两轮饱和；调用、来源或时长预算不足；达到该 run 冻结的 `max_research_rounds`。默认 `max_research_rounds` 为 4，允许范围是 1 到 8。四者是并列停止条件，满足其一即可，不要求同时成立。
- **FR-022**: 饱和必须定义为：本轮新纳入的相关性不少于 3 的论文数为 0，且没有新填上的必填单元格。连续饱和必须由程序按笔记顺序计数。
- **FR-023**: 研究页面必须按轮次显示已执行动作、被拒绝动作和未满足问题。一次状态查看必须返回当前轮次、未满足子问题和停止原因，不得等待整个研究循环结束。
- **FR-024**: 旧模式快照必须继续走 plan、approve_plan、retrieve、screen、select、read、analyze、decide、write、validate、finalize。旧模式来源请求上限必须仍是 20，模型调用上限必须仍是 150。legacy 与 coverage 必须按各自 run 快照并存；同一项目可以同时保留两种运行，一条运行不得改写另一条的快照。
- **FR-025**: 在新研究循环完成前，也就是本变更的阶段 6 结束前，开发默认必须保持 `planner_mode=legacy`。阶段 6 指研究循环已经接入运行，且旧模式测试仍然通过。
- **FR-026**: coverage 新运行的快照必须使用来源请求上限 40 和模型调用上限 180。该上限不得回写到已冻结的旧模式运行。
- **FR-027**: 语言范围含中文且没有已配置中文全文来源时，覆盖表必须写入 `zh_fulltext_not_licensed`。
- **FR-028**: 本变更不得包含知网或万方全文、任意网页、任意地址、命令执行、数据查询、角色之间互相调用外部工具，也不得把协调、检索、阅读、综述四类角色改成自由群聊，不得更换前端框架。
- **FR-029**: 外部工具入口必须仍是现有 9 个。调度必须依据覆盖表、动作清单和运行时准入。
- **FR-030**: 默认模型和论文来源必须保持模拟。真实模型和真实论文来源必须显式开启，调用必须记入现有预算账本。真实来源测试必须默认跳过。
- **FR-031**: 角色必须仍是协调、检索、阅读、综述四类。摘要筛选和抽取必须沿用现有阅读职责。规划不得直接接触外部来源。
- **FR-032**: 语义排序不可用时，篇内检索必须继续使用现有关键词相关度，并在该轮笔记中标明排序方式。

### Key Entities *(include if feature involves data)*

- **研究规格**: 一次 coverage 运行在检索前确认的合同。包含子问题、纳入和排除规则、抽取列、每个子问题的覆盖目标，以及用户给出的范围。
- **覆盖表**: 由项目账本算出的本轮缺口。包含每个必填单元格的填充情况、未满足子问题、剩余预算、最近一轮新的高相关论文数、连续饱和轮数和语料限制。
- **轮次动作**: 一轮中有限的封闭动作。类型只包括检索、一跳引文、全文阅读、篇内片段和停止。每轮最多 6 个；停止一旦被接受，就是该轮唯一动作。
- **研究笔记**: 每一轮追加的一页记录。包含已执行动作、被拒绝动作、新论文、新填上的列、未完成缺口和当时的排序方式。规划只能回看最近两页。
- **主张**: 绑定到一篇论文、一个子问题、一个抽取列、一条已有 evidence 和一种极性的可引用判断。极性为支持或反驳。
- **证据**: 既有的原文位置记录。主张只能引用同一篇论文上已经存在的证据。页码属于证据，不属于模型输出。
- **项目论文**: 项目级文献库中的论文，状态为在库、钉住或排除。同一项目的后续运行复用这些状态。
- **运行输入快照**: 一条 run 的执行依据。coverage 运行在 `approve_spec` 冻结 `planner_mode`、`max_research_rounds`、`max_actions_per_round`、`max_citation_neighbors`、`max_search_in_paper_calls_per_paper`、`embedding_mode`、`enabled_sources`，以及来源请求上限、模型调用上限和精读篇数上限。legacy 运行保存自己的旧模式快照，不经过 `approve_spec`。执行期间只读本 run 的快照。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在一次 coverage 运行中，用户能在任何论文检索发生前确认 3 到 5 个子问题、至少一条纳入或排除规则、至少一列抽取字段，以及每个子问题一个覆盖目标。
- **SC-002**: 当第一轮后仍有必填缺口且预算足够时，第二轮查询与第一轮不同，并且审阅者能把第二轮查询对应到覆盖表中的具体缺口。
- **SC-003**: coverage 综述里每一条点名论文的文献判断都能打开到主张，这些主张全部指向已有证据记录。
- **SC-004**: 同一项目的下一次运行在自己的检索开始前，能列出此前入库论文、钉住项和排除项；被排除论文不出现在新候选集中。
- **SC-005**: 旧模式运行仍能按原来的 11 个阶段完成，其冻结的来源请求上限和模型调用上限仍分别是 20 和 150。
- **SC-006**: 研究进行中，用户无需等待全部轮次结束，就能看到当前轮次、已执行动作、被拒绝动作和未满足问题。
- **SC-007**: 使用过期计划版本的确认被拒绝。coverage 运行确认成功后，即使进程配置随后改变，`approve_spec` 冻结的字段仍与确认时一致。同一项目中的 legacy 运行仍按自己的快照走原阶段。
- **SC-008**: 本变更的完成不依赖真实供应商小样本、桌面或编辑器客户端、人工评价集、另一套数据库版本、容器交付或备份恢复演练。

## Assumptions

- 行为细节以 `docs/superpowers/plans/2026-11-08-planning-memory-tools-refactor.md` 第 2、7、9、12 节为准。快照字段清单同时对照该计划第 5 节，只采用字段名称和冻结时机，不在本规格选择实现方案。
- 项目宪章 1.0.0 的九条规则继续有效。本规格不改写角色、模拟默认、旧模式快照、原文跨度、封闭工具、恢复前确认和单独验收项。
- 「阶段 6 结束」指新研究循环已经接入运行，并且旧模式测试仍然通过。在此之前，新运行的开发默认保持旧模式。
- 覆盖目标沿用每个子问题至少覆盖已有默认篇数的现有口径；用户可以在确认前修改目标。未指定时，每个子问题的默认覆盖目标是至少 3 篇已纳入论文，允许范围是 1 到 15。
- 抽取列的可选内容仍是方法、数据集、实验设置、指标、结果和局限。本变更不新增列类型。
- 时长预算沿用该次运行快照中的既有时长上限。本规格不另定一个新的时长数字。
- 高相关指相关性不少于 3。相关性为 2 且未钉住的论文可以保留在候选中，但不得精读。
- 摘要证据可以记录极性，但不得写成全文层面的实验结论。全文层面的实验判断仍要求原文片段和解析得到的页码。
- 同一篇论文的身份沿用现有去重规则：有稳定标识则并入已有论文，没有时按现有标题匹配规则处理。
- 界面只增加确认规格、查看轮次笔记和打开主张所需的内容，不更换现有前端框架。
- 真实供应商、中文全文授权、人工盲评，以及另一套运行环境的验收，仍按 `docs/implementation/acceptance-status.md` 单独计算，不算作本变更完成。
